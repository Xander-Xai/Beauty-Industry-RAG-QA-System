## Redis multi-worker session persistence

Tests: `tests/integration/test_redis_session_runtime.py`
Command: `RUN_RUNTIME_VALIDATION=1 python3 -m pytest tests/integration/test_redis_session_runtime.py -q`
Result: `6 passed`

- process A writes a dialog round with `QueryRewriteResult` + `locked_doc_ids` + async CLIP `RecallResult`
- a fresh process B restores them with correct Pydantic types/values
- process C observes process B's added round
- TTL is set to 7200 and refreshed on read
- Redis unavailable -> process-local memory fallback, no crash
- malformed payload / incompatible `schema_version` -> graceful fallback

## Redis multi-worker login rate limit

Tests: `tests/integration/test_login_rate_limit_runtime.py`
Command: `RUN_RUNTIME_VALIDATION=1 python3 -m pytest tests/integration/test_login_rate_limit_runtime.py -q`
Result: `4 passed`

- 6 attempts from one IP alternating across two independent processes: first 5
  ALLOWED, 6th blocked with HTTP 429 (shared Redis counter)
- key `ratelimit:login:<ip>` == "1" after one attempt
- window expiry: 1s window, 6th blocked then ALLOWED after TTL expiry
- Redis down: degrades to per-process memory limiting (still blocks the 6th
  within one process); this is single-worker limiting, not distributed

## Trusted proxy / `TRUSTED_PROXIES`

Harness: `scripts/validation/validate_trusted_proxy.py` (+ real `nginx:alpine`,
two uvicorn instances).
Command: `python3 scripts/validation/validate_trusted_proxy.py`
Result: `TRUSTED PROXY VALIDATION PASSED`

**Finding and fix:** uvicorn defaults to `proxy_headers=True` with
`forwarded_allow_ips=127.0.0.1`, so it rewrote `request.client.host` from
`X-Forwarded-For` *before* `api.routes_auth._get_client_ip` ran. A direct
localhost client could spoof its rate-limit identity even with `TRUSTED_PROXIES`
unset. Fixed in `app.py` by running uvicorn with `proxy_headers=False`; a
deterministic guard now enforces it.

- direct + no `TRUSTED_PROXIES`: forged `X-Forwarded-For: 9.9.9.9` ignored, resolves peer `127.0.0.1`
- single trusted nginx: resolves forwarded client `203.0.113.77`
- multi-hop nginx chain: walks right-to-left past the trusted hop and resolves `203.0.113.77`

## Known limitations

- Redis validation used one local server, not a cluster/Sentinel topology.
- Rate-limit HTTP-level multi-worker (`uvicorn --workers` behind a load
  balancer) was not exercised end to end; the shared-counter contract was
  proven at the process boundary.
- Only nginx was validated for proxy trust; Cloudflare / ALB / Traefik require
  their own `TRUSTED_PROXIES` configuration.
- Elasticsearch validation used a locally cached 8.11 image via an override;
  the committed compose pins 8.12.
- Prometheus validation is a single local scrape, not a long-run or Grafana/alerting validation.
- No production latency/QPS/quality claim is made.

## Evidence boundary

Local runtime validation != production benchmark.
No production latency/QPS/quality claim is introduced without reproducible evidence.
Deterministic unit tests and local multi-process/HTTP checks are not the same as
a deployed multi-worker/multi-node production run.
